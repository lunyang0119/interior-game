## 0. 설계 원칙

## 1. 복구 단계 (Restoration)

- **[C]** `data/rooms/<id>.json`에 `restore: [stage...]`. stage = `need[]` + `reward[]`.
  - need 타입 v1: `ruined_zero`, `placed`(layer/tag/item_id + count), `fish`(단계 시작 이후 납품 수, 종 필터 가능), `spend`/`pool`(재화).
  - reward 타입 v1: `unlock_exit`, `unlock_room`, `unlock_place`(맵 건물). ~~`unlock_tag`~~ → **[U]** 폐기(가구 잠금 안 함).
  - 저장: `room_meta` `stage:<방>`(완료 단계 수), `stage_ts:<방>`(완료 시각).
  - place/move/remove/납품 트랜잭션 끝에 `advance()` 한 번 → 완료 시 events 기록 + ws `progress` 브로드캐스트.
  - `GET /api/rooms`에 stage/progress 포함. 잠긴 출구/건물은 `locked` 플래그.
- **[U]** 1차 흐름: **여관 ruined 청소 → 필드 개방 → 낚시(납품) → 할당량 + 일정 재화가 모이면 2층 개방.**
- **[U+]** 부엌(요리를 하게 되면)은 여관과 이어진 방. 처음엔 ruined 가구로 가득, 일정 재화를 모아야 고칠 수 있음(복구 단계 재사용).
- **[C]** 클라: HUD 방 칩 `여관 · 2/3단계 ▰▰▱`, 탭하면 진행도 패널(need 체크리스트 + 보상 미리보기). 완료 순간은 전원 토스트 + 전용 SFX + 방 안 반짝 연출. 맵: ruined 남은 방 ❗, 진행 중 점 표시, 잠긴 건물 🔒.

## 2. 납품 선택지 (낚시 → 공통 패턴)

- **[U]** 낚은 순간 `[팔기 +N💰] [납품 k/m]` 두 버튼. 납품하지 않으면 지금처럼 즉시 돈.
- **[C]** 납품은 현재 열린 요구치(복구 단계·의뢰·월간 목표)에 바로 카운트 → **인벤토리 불필요**. 요구치가 없으면 팔기만 보임. 채집·광산 등 다른 획득 콘텐츠도 같은 UI 재사용.

## 3. 기록 패널 (Activity)

- **[U]** 로그인 팝업이 아니라 상점/아바타와 같은 급의 **패널**(하단 바 `📜 기록`, 접기에 포함). 언제든 열 수 있음.
- **[U]** **최근 5개만** 표시, 그 이하는 안 보임. 행동 기록과 **수입도 표시**("하나가 12💰 벌어왔어요") — 이야깃거리는 되되 순위표가 되지 않도록 5개 제한.
- **[C]** 상단 요약 카드(오늘 공동 자금 증감 · 낚시 수 · 현재 방 진행도). 서버: `events` 테이블(`007_events.sql`, ts/kind/room/player/item/amount/data) + `GET /api/activity` + ws `event`. 수입 이벤트는 sheet 갱신 시 player별 earned 차이로 생성. 기존 ledger는 시작 시 1회 백필.

## 4. 콘텐츠 아이디어

### A. 손님과 숙박료 — 핵심 루프 (채택)
- **[C]** 여관 복구 후 NPC 손님이 하루 1회 체크인, 방 **안락도**에 따라 숙박료를 공동 자금에 넣음. 꾸미기 = 수입. 손님 외형은 기존 캐릭터 생성기로 충분.
- **[U]** 안락도 공식 보강:
  - 가구 **가격이 높을수록** 안락도 ↑.
  - **세트 보너스**: 같은 스프라이트 시트(또는 같은 에셋 폴더) 출신 가구로만 구성된 방/구역 → 보너스. 출처는 빌드 파이프라인(`slices.json` 소스 경로)에서 자동 태깅 가능.
  - **침대 계열 가구가 없으면 숙박료 0.** `bed` 태그는 유저가 에디터에서 직접 태깅 → **에디터에 태그 입력 UI 필요**.
- **[U+]** **예약 손님**: 가끔 특정 가구를 요구하는 손님이 예약. 구비해 두면 일반 손님의 **2배** 지불, 못 갖추면 **다음날 손님이 아예 안 옴**.
- **[U+]** **개파 손님**: 한 달에 한 번 예약. 개가 없어도 안락도가 **높으면** 감안하고 옴, 낮으면 안 옴. (고양이 I와 세트 분위기)
- 설계 메모 **[C]**: 서버 일일 틱(KST 기준 하루 1회, 접속 없을 때도 돌아야 하므로 startup+타이머), 안락도는 방 items에서 순수 함수로 계산, 예약은 `room_meta`/별도 테이블에 "요구 item_id, 기한" 저장. 결과는 events에 "손님 3명이 15💰를 냈어요".

## 5. 추천 구현 순서 (Claude 제안, 유저 확정 전)

2. 기록 패널 5줄 (3장) — events 테이블, 수입 이벤트
3. F 메모·표지판 — 작고 바로 체감
4. A 손님·숙박료 — 안락도(가격·세트·침대) → 일일 틱 → 예약 손님 → 개파 손님
5. 에디터: 태그 입력 UI(`bed` 등), 세트(출처) 자동 태그를 `build`에 추가
6. C 채집 (에셋 확보 후) → B 의뢰 게시판(획득물만) → H 월간 목표
7. I 고양이 → G 광산 → E 텃밭 / D 요리 (에셋·인벤토리 확보 후)

각 단계 끝나면 멈춰서 보고. 결정은 유저가, 커밋도 유저가.

## 6. 미결 사항

- 안락도 공식의 구체 수치(가격 가중, 세트 보너스 배율, 고양이 애착 가중) — 구현 때 초안 제시.
- 손님 수/숙박료 스케일: 공동 자금 단위(아이템 가격 2~60💰)와 균형 필요.
- 예약 손님 요구 가구 선정 방식(가격대·층 랜덤? 상점에 있는 것만?).
- 월간 목표의 생성 규칙(수동 데이터 vs 서버 자동 생성).
- **풀 인플레이션**(2026-10-10 메모): 돈 싱크가 사실상 없다 — 가구는 팔면 전액 환불(돈이 가구에 주차될 뿐), 복구의 `pool` 조건은 확인만 하고 소비하지 않음, 유일한 싱크는 납품. 여관을 다 꾸미면 숙박료가 매일 쌓이는데 쓸 데가 없어 잔액이 의미를 잃는다. 페널티 없는 대처: 월간 목표의 금액 조건을 수천 단위로 크게, 또는 소비형 콘텐츠(광산 입장료·텃밭 씨앗·복구 단계의 "기부" 조건). 나중에 다룸.
